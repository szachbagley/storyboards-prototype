⏺ I read the compiler, the generation service, the schema, and both skills.
  Here's my thinking.

  The mechanism

  There are three plausible ways to carry continuity, and I think only one
  survives contact with your invariants.

  previous_interaction_id chaining is the one the spec already names (§53, §507)
  and I'd stay away from it — not just because it's deferred, but because it
  breaks invariant 7. A chained generation isn't reproducible from its own
  input_snapshot; the provenance lives on Google's servers under an ID whose
  lifetime your own spec flags as undocumented. It also has no answer for "user
  regenerated frame 2" — the chain points at an interaction that is no longer
  the selected image. Wrong primitive.

  Predecessor's frame description as text context is cheap and free of the
  reference budget, but it puts two scenes in one prompt. That's precisely the
  failure mode the identity-only rule exists to prevent, applied at a different
  layer. I'd skip it.

  The predecessor's selected image as an extra, distinctly-labeled reference 
  part. This is the same mechanism that already holds character identity, which
  means it inherits everything you've already built: bytes read from S3 by the
  caller, compiler stays pure, snapshot records the source, fully auditable
  after the fact. This is my recommendation.

  What that costs and touches

  - One reference slot. MAX_TOTAL_CONCEPTS = 10 is the model's high-fidelity
    object cap, so validation becomes concepts + (continuity ? 1 : 0) ≤ 10 —
    with continuity on, nine concepts, not ten. I would not count it against the
    character cap of 4; it isn't a character reference. Worth watching
    empirically though — a previous frame containing three faces may interact
    with the consistency budget in ways the docs don't describe.
  - Ordering (invariant 5). Append it last, after the concept image parts, with
    its text mention in a section after the reference list. Appending keeps
    concept numbering stable and keeps the label↔part correspondence trivially
    checkable.
  - It must not be labeled "Reference image N." The FORMAT_PREAMBLE says
    "Reproduce each referenced subject faithfully" — pointed at the previous
    frame, that instruction says "redraw this image," which is the opposite of a
    continuation. The continuity part needs its own section with explicit
    override language: match the treatment, do not reproduce the composition or
    camera.
  - Prompt text is skill-owned. The new constant belongs in
    storyboard-prompt-compiler/SKILL.md alongside FORMAT_PREAMBLE, since the
    byte-identity test is what keeps it honest.

  Resolution and edge cases

  I'd resolve the predecessor implicitly — the frame at the next-lower position,
  resolved at generation time, driven by a boolean
  frames.continues_from_previous. One column, no FK, no cycle check, and
  reordering or deleting a frame just works: continuity follows the sequence
  rather than pinning to a row.

  Three cases need decisions, and two have obvious answers:

  - Which image? The predecessor's selected_generation_id — the canonical "this
    is the frame" pointer, not the newest.
  - Chain depth? One hop only. Frame 4 sees frame 3, not 1–3. Drift will
    accumulate; that's inherent and worth saying out loud in the UI rather than
    engineering around.
  - Predecessor has no selected generation? I'd fail with a specific 422 
    continuity_source_missing rather than silently degrading — silent
    degradation here produces a frame that looks fine and isn't continuous,
    which is exactly the class of bug this codebase keeps trying to avoid. The
    first frame in a story hides the control entirely.

  One thing I'd deliberately not build: invalidation. Regenerate frame 2 after
  frame 3 exists and frame 3 is now stale against its source. The snapshot
  records which generation was used, so it's diagnosable, but automatic
  re-generation is a rabbit hole and costs money without asking.

  Two decisions genuinely change the implementation, so I'd rather not guess:

  Revised design

  Schema — a self-referential nullable FK, as you picked:

  ALTER TABLE frames
    ADD COLUMN continues_from_frame_id UUID
    REFERENCES frames(id) ON DELETE SET NULL;

  The guards, reduced. I listed four; I now think you only need two.

  - Same story — required, and it's the one that matters. Resolve the target
    with getFrameById(targetId, userId) and compare storyId. That single check
    gives you ownership transitively, and a cross-account target returns the
    same "unknown frame" as a nonexistent one, so the endpoint isn't an
    existence oracle (invariant 10).
  - Not self — trivial, required.
  - Cycle — skip it. Nothing traverses the chain. Generation reads exactly one
    hop: target frame → its selected generation → its image. A→B→A produces no
    loop, no recursion, no bug; it just looks incoherent in the UI. Recursive
    cycle detection here would be machinery guarding against a failure that
    can't occur.
  - Forward references — don't enforce, just don't offer. Requiring
    target.position < frame.position is tempting (it makes cycles structurally
    impossible too), but reordering would break it after the fact, so it isn't
    really an invariant. Better: the picker only lists frames earlier in the
    story, and the API doesn't enforce ordering. Reorder then produces an odd
    link rather than an invalid one.

  The prompt constant needs rewording. Your chosen semantics are right, but "the
  frame immediately preceding this one" is now false — an explicit pick may be
  three frames back. Also note the compiler is pure and can't know render-time
  labels like "Frame 3", so the reference stays generic:

  Continuity reference — an earlier frame from this same sequence. Match its
  rendering style, palette, lighting, and the state of the world it depicts,
  so the two frames read as part of one continuous scene.

  Do NOT reproduce its composition, staging, or camera. The scene below
  describes a new shot.

  One silent-failure hole to accept knowingly. ON DELETE SET NULL means deleting
  the target frame quietly drops continuity from every frame pointing at it,
  and a nulled link is indistinguishable from one never set. The next generation
  just comes out non-continuous with no error. I'd accept it for a POC rather
  than add a tombstone column, but it should be written down rather than
  discovered.

  Error-code placement. continuity_source_missing (target has no selected
  generation) is a request-time AppError like too_many_concepts — raised before
  the pending row exists. It does not belong in GENERATION_ERROR_CODES; that
  taxonomy is for failures of a generation already in flight.

  Everything else from before holds: image part appended last, concepts + 1 ≤ 
  MAX_TOTAL_CONCEPTS, doesn't count against the character cap, one hop, snapshot
  records { frameId, generationId, imageKey }, new constant transcribed into
  storyboard-prompt-compiler/SKILL.md under the byte-identity test.

  The first thing to check if output looks wrong: FORMAT_PREAMBLE still says
  "Reproduce each referenced subject faithfully." The continuity section
  contradicts it deliberately and comes later in the prompt, which should win —
  but if generations come back as redraws of the continuity frame rather than
  new shots, that tension is the cause, and the fix is branching the preamble
  when continuity is present.

  Want me to write this up as continuity-plan.md in the repo convention
  (alongside identity-plan.md), or go straight to implementing it?
